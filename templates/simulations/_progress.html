{% comment %} The polling fragment. One root element, swapped whole. While the run is unfinished this element carries its own hx-trigger, so it asks for its own replacement every two seconds. When the run reaches a terminal state the replacement comes back WITHOUT those attributes and the polling stops because nothing is left to poll with - and the view adds an HX-Refresh header, so the page reloads once and the report appears. Phase 10 T3.1: the bar is smoothed by static/js/run-progress.js, which reads the `data-*` below - the real share, the seconds since the run was asked for and the seconds it should take (`pace`, from the view) - and shows the largest of the value it showed last, the real one and a curve that slows as it nears 95%. It keeps that value across the swaps, never goes backwards and never reaches 100 before the run is done; while the run waits in the queue (`data-queued`) it stays under 10%. Without the script: the real bar. The panel around this fragment is in detail.html. {% endcomment %} {% load humanize l10n %}
